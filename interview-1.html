High Scale & Ingestion ISO-20022 Payments

Did you design a microservice handling millions of data in minutes? Give a real banking production example.

Executive Interview Response (STAR Framework)

Situation: At JPMC Core Clearing & Settlement, our inbound Fedwire/CHIPS ingest engine had to absorb over 6.5 million ISO-20022 wire messages in under 4 minutes during the morning liquidity window opening, without dropping messages, exceeding ledger lock limits, or causing duplicate fund transfers.

Action: 1. Decoupled Edge from Ledger: Built non-blocking ingestion using Spring Boot 3 WebFlux (Netty). Ingest pods only validate cryptographic signatures and write to Kafka. 2. Partitioning Strategy: Configured Kafka topics with 128 partitions keyed deterministically by MurmurHash2(accountNumber) to guarantee strictly serial processing per account without global locks. 3. Distributed Deduplication: Used Redis Bloom Filter coupled with Redis sliding-window TTL locks to short-circuit 99.9% of replay attempts before hitting Postgres. 4. Batched Persistence: Consumer workers process in chunks of 500, executing batched JDBC SQL (rewriteBatchedStatements=true) with manual asynchronous Kafka offset commits.

Result: Scaled seamlessly to 48 EKS pods on AWS, processing 6.5M transactions in 3.4 minutes (peak 52,000 TPS) with zero duplicate postings, 0 dropped messages, and P99 latency of 42ms.

Spring WebFlux Ingestion Controller with Reactive Kafka 
@RestController
@RequestMapping("/api/v1/payments")
@RequiredArgsConstructor
@Slf4j
public class PaymentIngestController {

    private final ReactiveKafkaProducerTemplate<String, PaymentWireDto> kafkaTemplate;
    private final ReactiveRedisTemplate<String, String> redisTemplate;

    @PostMapping(value = "/wire", consumes = MediaType.APPLICATION_JSON_VALUE)
    @ResponseStatus(HttpStatus.ACCEPTED)
    public Mono<PaymentAck> ingestWirePayment(@Valid @RequestBody PaymentWireDto wire) {
        String dedupeKey = "dedupe:wire:" + wire.getInstructionIdentification();

        // 1. Non-blocking Redis distributed lock check
        return redisTemplate.opsForValue()
            .setIfAbsent(dedupeKey, "QUEUED", Duration.ofHours(24))
            .flatMap(isNew -> {
                if (!Boolean.TRUE.equals(isNew)) {
                    log.warn("Duplicate payment rejection: {}", wire.getInstructionIdentification());
                    return Mono.error(new DuplicatePaymentException("Wire instruction already received"));
                }

                // 2. Deterministic partition key based on sender account
                String partitionKey = wire.getDebtorAccount().getIban();

                // 3. Dispatch to Kafka without waiting for downstream ledger commit
                return kafkaTemplate.send("payments.fedwire.inbound.v1", partitionKey, wire)
                    .map(senderResult -> new PaymentAck(
                        wire.getInstructionIdentification(), 
                        "QUEUED", 
                        Instant.now()
                    ));
            });
    }
}

P1 Incident Triage HikariCP Pool Depletion

Give a scenario where you handled a prod issue. What exact triage steps did you take in Spring Boot microservices?

Post-Mortem: Cascading Database Starvation via Blocked Transaction Boundary

The Incident: During peak trading at 11:15 AM EST, all 18 instances of our Payment Execution microservice started failing health probes (/actuator/health). Ingress latency spiked from 35ms to 30,000ms, producing HTTP 504 Gateway Timeouts across core banking consumers.

Root Cause: A downstream AML/Sanctions REST service experienced internal deadlocks, causing response times to balloon from 15ms to 25 seconds. In our code, an engineer had annotated the orchestration method with Spring's @Transactional, placing the external HTTP REST call inside the active database transaction. HikariCP held physical DB connections open for 25 seconds waiting on the remote socket, exhausting the entire pool of 50 connections in <2 seconds across all pods.

1. Triage & Shed Traffic

Inspected Dynatrace Service Flow. Noticed 98% of Tomcat threads blocked in HikariPool-1.getConnection(). Used API Gateway rate-limiter to shed 50% non-critical traffic.

2. Telemetry Capture

Captured thread dumps via jcmd 1 Thread.print > /tmp/threads.tdump before pods crashed. Verified 200 Tomcat threads in TIMED_WAITING on socket read from the AML host.

3. Fast Mitigation Hotfix

Refactored code to remove the HTTP call from @Transactional. Wrapped AML client in a Resilience4j TimeLimiter (800ms) and Circuit Breaker with fallback queuing.

4. Long-Term Hardening

Configured connection-timeout: 3000ms and leak-detection-threshold: 2000ms on HikariCP. Added Prometheus alerts on hikaricp_pending_threads > 5.

Distributed Tracing W3C TraceContext • OpenTelemetry

How do you trace microservices? Who generates TraceId and SpanId? Explain Sleuth vs. Micrometer Tracing.

ID Generation Lifecycle

  • • Trace ID: A 128-bit globally unique identifier created by the first edge service (API Gateway or Ingress controller) upon request arrival. Propagates unchanged across every downstream network hop (HTTP, Kafka, gRPC).
  • • Span ID: A 64-bit identifier representing a discrete segment of execution (e.g., executing a DB query or publishing an event). Created anew by each microservice.
  • • Parent Span ID: Captures the caller's Span ID, enabling APM tools (Dynatrace, Zipkin) to construct the hierarchical Directed Acyclic Graph (DAG).

Spring Cloud Sleuth vs Micrometer Tracing

  • • Spring Boot 2.x (Sleuth): Used legacy B3 propagation headers (X-B3-TraceId, X-B3-SpanId). Sleuth directly manipulated thread-locals and was tightly bound to Brave.
  • • Spring Boot 3.x (Micrometer Tracing): Sleuth is deprecated. Micrometer Tracing is a vendor-neutral facade supporting OpenTelemetry (OTel) or Brave tracers. Standardizes on W3C TraceContext headers (traceparent: 00-{traceId}-{spanId}-{flags}).

Kafka High Performance OS Page Cache • Zero-Copy

How do you make sure Kafka achieves maximum throughput while guaranteeing zero data loss?

In financial payment pipelines, maximum throughput must never compromise durability. Throughput is achieved by optimizing batching density, reducing system call context switches, and utilizing Linux kernel zero-copy network transfer (sendfile()).

Producer Optimization Matrix

  • • batch.size: 131072 (128 KB) vs default 16 KB. Packs multiple payment messages into a single memory record batch.
  • • linger.ms: 10ms. Introduces a tiny 10ms delay to allow batches to consolidate, increasing throughput 4x.
  • • compression.type=lz4 / zstd: Compresses batches in memory before transmission, minimizing network bandwidth and broker disk IO.
  • • acks=all (-1) & min.insync.replicas=2: Broker requires acknowledgment from leader and at least one follower before succeeding.
  • • enable.idempotence=true: Producer assigns monotonic sequence numbers per partition, preventing duplicate records on network retry.

Consumer & Kernel Optimization

  • • fetch.min.bytes: 1048576 (1 MB) and fetch.max.wait.ms=500 prevent brokers from returning fractional micro-responses.
  • • max.poll.records: 1000 items processed per poll, bounded to stay well within max.poll.interval.ms (300000ms).
  • • CooperativeStickyAssignor: Eliminates "Stop-The-World" consumer group rebalancing storms during pod rollouts.
  • • Zero-Copy IO: Kafka brokers bypass userspace memory entirely, copying disk page cache directly to NIC sockets via sendfile().

Batch Processing Remote Chunking • State Recovery

Did you handle complex batch processing of millions of data in hours? What if it fails midway?

Production Scenario: End-of-Day (EOD) 20 Million Ledger Reconciliation

The Challenge: Reconcile and calculate interest accruals on 20+ million accounts within a 2-hour SLA window (1:00 AM to 3:00 AM). Single-JVM execution fails at this volume due to memory overhead, garbage collection pauses, and DB connection serialization.

1. Master-Worker Partitioning

A master coordinator step queries primary key ranges (min_id to max_id) and dynamically spawns 64 discrete partitions transmitted across Kafka to worker pods running in Kubernetes.

2. Chunking & Commit Intervals

Workers stream data using JdbcPagingItemReader in chunks of 5,000 items. Each chunk is committed in an isolated database transaction, recording offset checkpoints in BATCH_STEP_EXECUTION_CONTEXT.

3. Mid-Flight Crash Recovery

If a pod terminates at record 42,000 of a 100,000 slice, the job is restarted with the same JobParameters. Spring Batch skips the 40,000 already committed records and resumes at 40,001.

Resilient Spring Batch Configuration with Skip & Retry Policies 
@Bean
public Step reconciliationStep(
        JobRepository jobRepository, 
        PlatformTransactionManager txManager,
        ItemReader<SettlementLedger> reader,
        ItemProcessor<SettlementLedger, InterestPosting> processor,
        ItemWriter<InterestPosting> writer) {

    return new StepBuilder("reconciliationStep", jobRepository)
            .<SettlementLedger, InterestPosting>chunk(5000, txManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .skip(CorruptRecordException.class)
            .skipLimit(100)                     // Route corrupted records to reconciliation quarantine table
            .retry(OptimisticLockException.class)
            .retryLimit(3)                      // Auto retry concurrency updates
            .listener(new ChunkExecutionRecoveryListener())
            .build();
}

Disaster Recovery Transactional Outbox • GitOps

How do you handle Producer and Consumer behavior if Kafka goes completely down? Who creates partitions in enterprise prod?

What Happens When Kafka Fails?

• Producer Backpressure & Outbox: If Kafka brokers are unreachable, producers block until max.block.ms=3000. A Resilience4j Circuit Breaker trips and routes all pending messages to an Outbox Table in PostgreSQL within the local database transaction (Transactional Outbox Pattern). A Debezium CDC engine or secondary poller streams outbox records to Kafka once brokers recover.

• Consumer Backoff: Consumers initiate exponential backoff retry loops, pausing partition consumption via pause() without crashing pods.

Who Creates Partitions in Enterprise Prod?

• Strict Governance Rule: auto.create.topics.enable=false is permanently disabled across all enterprise clusters.

• Microservices are strictly forbidden from creating topics or altering partitions at runtime.

• Topics are managed as Code via Terraform or Strimzi KafkaTopic CRDs in a GitOps repository. Any partition expansion is planned with partition reassignment tools to prevent hot brokers.

Resilient Outbox Fallback Publisher with Circuit Breaker 
@Service
@Slf4j
@RequiredArgsConstructor
public class ResilientPaymentProducer {

    private final KafkaTemplate<String, PaymentPayload> kafkaTemplate;
    private final OutboxRepository outboxRepository;

    @CircuitBreaker(name = "kafkaBrokerCB", fallbackMethod = "writeToDatabaseOutbox")
    public void publishPaymentEvent(PaymentPayload payload) {
        // Normal high-speed streaming path
        CompletableFuture<SendResult<String, PaymentPayload>> future = 
            kafkaTemplate.send("payments.settlement.v1", payload.getAccountId(), payload);

        future.whenComplete((result, ex) -> {
            if (ex != null) {
                log.error("Async send failed for ID: {}. Routing to Outbox.", payload.getId());
                writeToDatabaseOutbox(payload, ex);
            }
        });
    }

    // Fallback invoked if Kafka is down or circuit is OPEN
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void writeToDatabaseOutbox(PaymentPayload payload, Throwable ex) {
        log.warn("KAFKA DOWN. Writing transaction {} to PostgreSQL Outbox Table", payload.getId());
        outboxRepository.save(new OutboxEntity(
            payload.getId(),
            payload.toJson(),
            OutboxStatus.PENDING_KAFKA_RESTORE,
            Instant.now()
        ));
    }
}
