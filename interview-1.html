High Scale Payments Ingestion

Did you design a microservice that handles millions of data in minutes? Give a real production example.

Quick Interview Pitch (Say This First): "Yes. Our payment ingestion service handles about 4-5 million transactions in under 4 minutes at market open. A normal Spring MVC service ran out of threads when the database got slow, so we moved the entry point to WebFlux, which needs far fewer threads. It checks Redis to drop duplicates, puts the payment on a Kafka topic (keyed by account so order is kept), and returns right away. Consumers then save payments to PostgreSQL in batches of 500. Fast at the front, safe at the back."
Production Reality (The 6+ YOE Perspective):

• Why Tomcat / standard MVC failed: Thread-per-request model exhausted 200 Tomcat worker threads in seconds when downstream databases had a slight spike in latency.

• How we fixed it: Switched to Spring WebFlux Netty edge service (takes 15MB RAM per pod, uses event loop). It writes to Kafka (128 partitions, keyed on accountId so all transfers for one account stay strictly ordered).

• Database layer: Rather than doing 1 row insert per event, consumers accumulate 500 records and run a single SQL INSERT INTO payments VALUES (...), (...) ON CONFLICT DO NOTHING using JDBC batching.

WebFlux + Redis Non-Blocking Dedupe & Kafka Publish 
@PostMapping("/wire/ingest")
public Mono<ResponseEntity<PaymentAck>> ingestWire(@Valid @RequestBody WirePaymentRequest request) {
    String dedupeKey = "dedupe:wire:" + request.getInstructionId();

    // 1. Redis non-blocking atomic check (TTL 24 hrs)
    return redisTemplate.opsForValue()
        .setIfAbsent(dedupeKey, "PROCESSING", Duration.ofHours(24))
        .flatMap(isNew -> {
            if (!Boolean.TRUE.equals(isNew)) {
                return Mono.just(ResponseEntity.status(HttpStatus.CONFLICT).build());
            }
            // 2. Partition by Account IBAN to keep FIFO sequence per customer
            return kafkaTemplate.send("payments.wire.inbound", request.getSenderAccount(), request)
                .map(result -> ResponseEntity.accepted().body(new PaymentAck(request.getInstructionId(), "QUEUED")));
        });
}

WebFlux Pipeline & Errors

Why did you use WebFlux? How do you write a WebFlux pipeline and handle exceptions?

Simple Answer (Say This): "Normal Spring MVC gives one thread to each request, and that thread just sits and waits while we call Redis, Kafka or another API. When traffic spikes, we run out of threads even though the CPU is idle. WebFlux uses a few event-loop threads that never wait - they start the call, move on, and come back when the response arrives. So the same pod handles many more requests. I write the logic as one chain: validate, then check Redis, then publish to Kafka, then return the response. Errors are handled inside the chain, not with try/catch."
In Plain Words:

• Why WebFlux: Our service mostly waits on I/O (Redis, Kafka, REST calls). Waiting threads are wasted memory. Think of a waiter who takes your order and walks away instead of standing at your table until the food is ready.

• When NOT to use it: If the code is CPU-heavy or uses blocking JDBC/JPA, WebFlux gives no benefit. Plain MVC is simpler. We only used it at the edge ingestion service.

• Pipeline idea: Each step returns a Mono (0 or 1 result) or Flux (many). Nothing runs until someone subscribes - Spring does that for us.

• Exceptions: A thrown exception inside a chain becomes an error signal. We handle it with onErrorResume (fallback), onErrorMap (convert to our business exception) and retryWhen with backoff for temporary failures. One global @RestControllerAdvice turns the final exception into a clean 400/409/503 response.

• Biggest mistake to avoid: Never call blocking code (JDBC, .block(), Thread.sleep) on the event loop. It freezes every request on that thread. If unavoidable, wrap it in Schedulers.boundedElastic().

WebFlux Pipeline + Error Handling 
public Mono<PaymentAck> process(WirePaymentRequest req) {
    return validate(req)                                   // 1. validate
        .flatMap(r -> dedupe(r))                           // 2. Redis check
        .flatMap(r -> kafkaSender.send(r))                 // 3. publish to Kafka
        .map(r -> new PaymentAck(r.getInstructionId(), "QUEUED"))
        .timeout(Duration.ofSeconds(2))                    // never wait forever
        .retryWhen(Retry.backoff(3, Duration.ofMillis(100))
            .filter(e -> e instanceof TransientException)) // retry only temporary errors
        .onErrorMap(TimeoutException.class,
            e -> new ServiceUnavailableException("Kafka slow"))
        .doOnError(e -> log.error("wire failed id={}", req.getInstructionId(), e));
}

@RestControllerAdvice
public class GlobalErrorHandler {
    @ExceptionHandler(DuplicatePaymentException.class)
    public ResponseEntity<String> dup(DuplicatePaymentException e) {
        return ResponseEntity.status(409).body(e.getMessage());
    }
    @ExceptionHandler(ServiceUnavailableException.class)
    public ResponseEntity<String> unavailable(ServiceUnavailableException e) {
        return ResponseEntity.status(503).body("Try again later");
    }
}

Kafka Batch Consumer

Did you use Kafka in batch? What problems did you face in prod and how did you resolve them?

Simple Answer (Say This): "Yes. Our consumers read records in batches of around 500 and save them to the database with one bulk insert, because one insert per message was far too slow. In production we hit three real problems: rebalancing loops when one batch took too long, one bad message blocking the whole partition, and duplicates after a restart. We fixed them by tuning poll settings, sending bad records to a dead-letter topic, and making the database write idempotent."
Problem 1: Constant Rebalancing

What happened: A batch of 500 took longer than max.poll.interval.ms. Kafka thought the consumer was dead and moved its partitions, so the same records were read again - a loop.

Fix: Lowered max.poll.records to 200, raised the poll interval, and made the DB insert faster.

Problem 2: Poison Message

What happened: One record with bad data made the whole batch fail. It retried forever and the partition lag kept growing.

Fix: Retry 3 times, then send that record to a .DLT (dead-letter topic) and move on. Alert on DLT count.

Problem 3: Duplicates

What happened: Pod crashed after the DB save but before the offset commit. After restart the batch was processed again.

Fix: Kafka is "at least once", so we made the insert safe to repeat: ON CONFLICT DO NOTHING on the instruction id.

Also Mention:

• We commit offsets manually after the DB write succeeds, never before.

• We watch consumer lag in Grafana/Dynatrace. Rising lag = consumers are too slow, so we add pods (up to the partition count).

Kafka Batch Listener with DLT 
# application.yml
spring.kafka.consumer:
  enable-auto-commit: false
  max-poll-records: 200
  properties:
    max.poll.interval.ms: 300000

@KafkaListener(topics = "payments.wire.inbound", batch = "true")
public void consume(List<ConsumerRecord<String, WirePayment>> records, Acknowledgment ack) {
    List<WirePayment> payments = records.stream().map(ConsumerRecord::value).toList();
    jdbcRepo.bulkInsertIgnoreDuplicates(payments); // INSERT ... ON CONFLICT DO NOTHING
    ack.acknowledge();                              // commit offset only after DB success
}

@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    // retry 3 times (1s apart), then send to payments.wire.inbound.DLT
    return new DefaultErrorHandler(new DeadLetterPublishingRecoverer(template),
                                   new FixedBackOff(1000L, 3));
}

Production P1 JVM Memory

What memory issues did you face in production and how did you solve them?

Simple Answer (Say This): "Our pods kept getting killed by Kubernetes with OOMKilled, and every few days memory would slowly climb. I took a heap dump and found two causes. First, a report API loaded 2 million rows into a List, so one request used gigabytes. Second, a static HashMap cache that never removed old entries - a classic memory leak. I fixed the first with pagination and streaming, and the second by switching to a Caffeine cache with a size limit and expiry. I also set the JVM to use a percentage of the container memory."
Step 1: Confirm

Grafana heap graph went up like stairs and never came down after GC. Pod restarts showed OOMKilled.

Step 2: Capture

Added -XX:+HeapDumpOnOutOfMemoryError so the dump is saved automatically before the crash.

Step 3: Analyze

Opened the dump in Eclipse MAT. The "Leak Suspects" report showed a HashMap holding 60% of the heap.

Step 4: Fix & Verify

Bounded the cache, paginated queries. Watched memory stay flat for a week after release.

Other Memory Issues We Saw:

• Heap vs container mismatch: JVM -Xmx was almost equal to the pod limit. Metaspace, threads and buffers pushed it over. Fix: -XX:MaxRAMPercentage=70 so 30% stays free for non-heap memory.

• Unbounded Kafka/Reactor buffers: Producer was faster than the DB, so queued messages piled up. Fix: smaller max.poll.records and Reactor backpressure (limitRate).

• Too many threads: Each thread costs about 1MB stack. Capped the thread pools instead of creating new ones per request.

• Large objects: Loading a big file fully into a byte[]. Fix: stream it in chunks.

Production P1 HikariCP Pool Starvation

Give a scenario where you handled a prod issue. What exact triage steps did you take in Spring Boot?

Quick Interview Pitch: "We had a P1 outage during peak volumes where all 12 pods of our Settlement service started timing out and failing Kubernetes liveness probes. Using Dynatrace, I saw that 100% of Tomcat threads were in WAITING on HikariPool.getConnection(). An external sanction check REST API had slowed down from 50ms to 20 seconds, and an engineer had wrapped that remote HTTP call inside a Spring @Transactional method. That held DB connections open doing nothing, exhausting our connection pool."
Step 1: Metric Check

Checked Dynatrace Service Flow & Prometheus hikaricp_pending_threads=150. Pods were healthy on CPU/RAM but choked on DB connections.

Step 2: Thread Dump

Ran jcmd 1 Thread.print in container. 190 threads showed SocketInputStream.socketRead0() while holding a JDBC connection.

Step 3: Immediate Mitigation

Tripped manual circuit breaker on the sanctions check, enabling asynchronous queue fallback to shed thread pool pressure.

Step 4: Permanent Fix

Moved the HTTP call outside the DB transaction. Set HikariCP connection-timeout=3000ms and Resilience4j timelimiter=1000ms.

Fix: Separate Remote Call from Database Transaction Boundary 
@Service
@RequiredArgsConstructor
public class PaymentExecutionService {
    private final SanctionsClient sanctionsClient; // Remote REST
    private final PaymentLedgerRepository ledgerRepo; // DB

    // DO NOT put @Transactional here! Remote call must happen outside DB lock.
    public void executePayment(PaymentRequest req) {
        // 1. External HTTP call with 800ms strict timeout & circuit breaker
        SanctionStatus status = sanctionsClient.verify(req); 
        
        // 2. Fast DB write in a quick isolated transaction (< 5ms)
        persistPaymentToLedger(req, status); 
    }

    @Transactional
    public void persistPaymentToLedger(PaymentRequest req, SanctionStatus status) {
        ledgerRepo.save(new LedgerEntry(req, status));
    }
}

Distributed Tracing TraceId & SpanId

How do you trace microservices? Who generates TraceId and SpanId? Explain Sleuth vs Micrometer.

Quick Interview Pitch: "TraceId identifies the whole customer request journey from end-to-end. It is generated by the first edge component—either the API Gateway or Ingress controller. A SpanId identifies a single unit of work inside one service (like a DB query or Kafka send), and each microservice generates its own new SpanId. In Spring Boot 2 we used Spring Cloud Sleuth with B3 headers; in Spring Boot 3 Sleuth was migrated to Micrometer Tracing with OpenTelemetry, standardizing on W3C headers (traceparent)."
Header Propagation Flow
Client HTTP → API Gateway: Generates TraceId = c4b81a, SpanId = 001
                ↓ Injects HTTP Header: traceparent: 00-c4b81a-001-01
Gateway → Payment Service: Reuses TraceId = c4b81a, New SpanId = 002
               ↓ Writes to Kafka Record Header: traceparent
Kafka → Ledger Service: Reuses TraceId = c4b81a, New SpanId = 003
How logs connect to traces automatically:

Micrometer Tracing automatically populates SLF4J MDC (Mapped Diagnostic Context) with traceId and spanId. When you log with Logback, every single line printed by your service includes the IDs, which ELK indexes for instant search.

Kafka Performance Zero Data Loss

How do you make sure Kafka achieves maximum throughput while guaranteeing zero data loss?

Quick Interview Pitch: "High throughput in Kafka comes from batching, compression, and partition concurrency, while zero data loss is governed by producer acknowledgments and broker ISR (In-Sync Replicas). In production, we set acks=all and enable.idempotence=true for durability. To get massive throughput, we add a tiny linger.ms=10 with batch.size=64KB and snappy compression so the producer sends dense compressed batches instead of individual network packets."
Producer Tuning:
  • • batch.size = 65536 (64KB) - Groups messages together.
  • • linger.ms = 10 - Waits up to 10ms to fill the batch.
  • • compression.type = snappy - Fast compression, low CPU overhead.
  • • acks = all & min.insync.replicas = 2 - Zero data loss.
Consumer Tuning:
  • • concurrency = 6 - Multiple threads per pod for partitions.
  • • max.poll.records = 500 - Batch process 500 records at once.
  • • CooperativeStickyAssignor - Smooth consumer rebalances without stopping the world.
  • • Linux OS utilizes sendfile() (Zero-Copy) to read disk cache directly to network.

Spring Batch State Recovery

Did you handle complex batch processing of millions of records in hours? What if it fails midway?

Quick Interview Pitch: "Yes, in our Nightly Ledger Reconciliation job, we process 15 million transactions in about 90 minutes. We use Spring Batch with Step Partitioning to split the data by account ranges across 16 parallel threads. We process items in chunks of 2,500. If the server crashes at record 1,000,000, we simply restart the job with the same JobParameters. Spring Batch checks its metadata tables (BATCH_STEP_EXECUTION_CONTEXT) and automatically skips the already committed chunks, resuming exactly where it crashed."
Interview Tip on 'Fail Midway':

Mention that you configure a FaultTolerant Step with a skipLimit(50) for bad records (like corrupted data formatting) and write them to a Dead-Letter DB table for audit, so that 1 malformed record does not abort the processing of 15 million valid records.

Observability ELK vs Dynatrace

Centralized Logging (ELK) vs Distributed Tracing (Dynatrace / Zipkin)? How do they work together?

Quick Interview Pitch: "Tracing tells you WHERE the problem is (which specific microservice or database query took 4 seconds out of a 5-second request). Logging tells you WHAT happened (the stack trace, SQL exception, or business error details). In our banking stack, they are tied together by the traceId. If Dynatrace flags a slow PurePath, I click a direct URL in Dynatrace that opens Kibana filtered by that exact traceId, showing the complete log narrative across every container."
Centralized Logging (ELK / Splunk):

Applications output JSON logs with traceId to stdout. Filebeat collects logs and ships them to Elasticsearch. Ideal for text search, audits, and viewing full stack traces.

Distributed Tracing (Dynatrace / OTel):

Measures latency per span and generates service dependency graphs. Tells you if latency was caused by network, DB lock contention, garbage collection, or downstream HTTP latency.

Resilience Outbox & GitOps

How do you handle Producer and Consumer behavior if Kafka goes completely down? Who creates partitions in enterprise prod?

Quick Interview Pitch: "If Kafka goes down, producers must never drop transactions. We use the Transactional Outbox Pattern: if the Kafka send times out, our Resilience4j circuit breaker trips and writes the payload to an OUTBOX_TABLE in PostgreSQL inside the local business transaction. Once Kafka recovers, a background worker or Debezium CDC reads the outbox and republishes. On the consumer side, pods pause consumption with exponential backoff without crashing. For partition creation: in enterprise banking, auto.create.topics.enable=false is mandatory; topics and partitions are strictly provisioned by Platform/DevOps teams via Terraform or GitOps CI/CD."
Transactional Outbox Fallback
[Payment Service] --1. Kafka Down?--> [Circuit Breaker Trips] → [Write into PostgreSQL OUTBOX table] → Return HTTP 202 Accepted.
[Debezium / Outbox Poller] --2. When Kafka Healthy--> [Streams records from OUTBOX to Kafka]

React & Frontend Virtualization & Memo

If a React page has too many DOM nodes and stutters, how do you stop excessive re-rendering?

Quick Interview Pitch: "When a UI with thousands of rows (like a real-time banking transaction blotter) freezes, the browser is overwhelmed by DOM size and unnecessary component re-renders. I fix this in three steps: 1. Windowing/Virtualization: Using @tanstack/react-virtual or react-window so only the 20 visible rows exist in the real DOM instead of 10,000. 2. Component Memoization: Wrapping row components in React.memo and ensuring callback props are memoized with useCallback so parent state changes don't re-render unaffected rows. 3. State Colocation: Moving fast-changing state (like a live search input) down into a dedicated child component so typing doesn't re-render the entire table grid."
1. DOM Virtualization

Instead of rendering 5,000 `<tr>` tags, only calculate height and render the 15 `<tr>` currently on screen. Eliminates DOM tree bloat.

2. Stable Prop References

Avoid passing inline objects `style={{color:'red'}}` or inline arrow functions `onClick={() => ...}` because they create new memory references on every render.

3. Input Debouncing

Debounce filter/search inputs by 250ms so filtering calculations don't fire on every single keystroke.

  const rowVirtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40, // 40px row height

            <TransactionRow tx={items[vRow.index]} onSelect={handleSelect} />
          </div>
        ))}
      </div>
    </div>
  );
}

Database Optimization EXPLAIN ANALYZE

If a complex SQL query takes too much time in production, how do you analyze, optimize, and redesign it?

Quick Interview Pitch: "I never guess with SQL performance. First, I run EXPLAIN (ANALYZE, BUFFERS) to see the query execution plan. Usually the issue is a Seq Scan (full table scan) on a multi-million row table, an unindexed JOIN condition, or an expensive OFFSET 50000. I optimize by creating a targeted composite index matching the WHERE and ORDER BY clause, replacing offset pagination with Keyset Pagination, and removing SELECT * to enable index-only scans. If the query is for reporting, I route it to a Read-Replica so it doesn't starve the primary write database."
Index & Query Fixes:
  • • Composite Index Rule (ESR): Exact match columns first, Sort columns second, Range columns last.
  • • Eliminate Offset: Keyset pagination (WHERE id < :lastSeenId ORDER BY id DESC LIMIT 50) runs in 2ms, whereas OFFSET 100000 scans and throws away 100,000 rows.
  • • Remove Correlated Subqueries: Convert nested subqueries inside SELECT to INNER JOIN or Common Table Expressions (CTE).
System Architecture Redesign:
  • • CQRS (Command Query Responsibility Segregation): Writes go to Oracle/Postgres primary; complex analytical queries hit Read-Replicas.
  • • Materialized Views / Redis Cache: Pre-aggregate daily customer balance totals every 10 minutes rather than doing runtime SUM(amount) on 5 million rows.
  • • Table Partitioning: Partition historical payment tables by Month (RANGE (created_at)) so the database only scans the current partition.

Integration 3rd-Party Vendor API

If one service calls an external 3rd-party vendor microservice, how do you handle logs and distributed tracing?

Quick Interview Pitch: "When calling external vendors (like Visa, LexisNexis, or Fedwire), you don't control their internal servers, so distributed tracing cannot cross into their code. Here is how I handle it: 1. Egress Client Interceptor: Using a RestClient or WebClient filter, I start a new client span and inject outgoing correlation headers (like X-Correlation-ID or W3C traceparent). 2. Capture & Correlate Vendor Reference: The vendor response usually returns their own tracking reference (vendorTransactionId). I immediately put that into our SLF4J MDC logs alongside our internal traceId. 3. PII Masking: External payloads contain card numbers or names; I ensure credit card numbers and SSNs are masked (************1234) before writing to ELK. 4. Hard Timeout Boundaries: I wrap every external call with a strict Resilience4j timeout (e.g., 1000ms) and log the vendor latency and HTTP status explicitly."
Production Vendor Client Interceptor (Spring WebClient / RestClient) 
@Component
@Slf4j
public class ExternalVendorLoggingInterceptor implements ClientHttpRequestInterceptor {

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body, ClientHttpRequestExecution execution) throws IOException {
        String internalTraceId = MDC.get("traceId");
        
        // 1. Inject our tracking ID so vendor support has it
        request.getHeaders().add("X-Correlation-ID", internalTraceId);
        
        long start = System.currentTimeMillis();
        try {
            ClientHttpResponse response = execution.execute(request, body);
            long duration = System.currentTimeMillis() - start;

            // 2. Extract vendor's returned tracking ID
            String vendorRef = response.getHeaders().getFirst("X-Vendor-Reference-ID");
            MDC.put("vendorRef", vendorRef != null ? vendorRef : "N/A");

            log.info("Vendor call to {} completed in {}ms with status={}", request.getURI().getHost(), duration, response.getStatusCode());
            return response;
        } catch (Exception ex) {
            log.error("Vendor call failed after {}ms: {}", (System.currentTimeMillis() - start), ex.getMessage());
            throw ex;
        } finally {
            MDC.remove("vendorRef");
        }
    }
}
