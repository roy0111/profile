Core Guide
State & Lifecycle

React Hooks & Lifecycle

Common hooks like useEffect, useState, useRef, rendering behaviors, and Strict Mode side effects.

Your React page is making the same API call multiple times when the component loads. What could be wrong?

Usually I would first check the useEffect dependency array. If useEffect does not have the correct dependency array, it can execute more often than expected. I would also check whether React Strict Mode is enabled in development, because React can intentionally run certain lifecycle logic twice in development to identify side effects. I would make sure the API call is inside useEffect with the appropriate dependencies and that the effect has proper cleanup when necessary.

A parent component changes state and a child component re-renders unnecessarily. How would you troubleshoot it?

I would use React DevTools Profiler to determine why the child is rendering. If the child receives objects, arrays, or functions created during every parent render, their references change even if their values are the same. I could use React.memo for the child and useMemo or useCallback for expensive values or callbacks when appropriate. I would avoid blindly using memoization everywhere because it also introduces complexity.

How would you handle loading, success, and error states for an API call?

I would explicitly model the request state instead of relying on a single boolean. For example, the UI should be able to distinguish between initial loading, successful data retrieval, empty results, and an error. With a server-state library, much of this state management is already provided. For a simple application, I could manage it using React state and useEffect.

What is the difference between useMemo and useCallback?

useMemo memoizes the result of a calculation, while useCallback memoizes the function reference itself. For example, I might use useMemo when calculating an expensive filtered dataset and useCallback when passing a callback to a memoized child component. I would use them based on an actual performance problem rather than automatically adding them everywhere.

Your React component receives new props but does not display the updated value. What could be wrong?

I would check whether the component is incorrectly memoized, whether the parent is mutating an object instead of creating a new reference, and whether the component has copied props into local state and that state has become stale. React relies heavily on state and prop references, so directly mutating objects or arrays can prevent expected updates.

A user navigates away from a page while an API request is still running. What would you do?

I would clean up the request when the component unmounts. With the Fetch API, I could use AbortController to cancel the request. This prevents unnecessary work and helps avoid updating state after the component is no longer relevant.

Performance & Virtualization

React Performance & Scaling

Optimizing render throughput, virtual lists, form performance, search debouncing, and expensive browser-side calculations.

Your React application becomes very slow when displaying 10,000 records. How would you improve it?

I would first determine whether the problem is rendering, API response time, or data processing. On the React side, I would avoid rendering all 10,000 records at once and use pagination or list virtualization. I could use techniques such as React.memo, useMemo, and useCallback where they actually reduce unnecessary work. I would also make sure the backend supports pagination rather than returning the entire dataset to the browser.

Your React application has a large form with 50 fields and typing becomes slow. What would you investigate?

I would profile the component first. If every keystroke causes the entire form to re-render, I would break the form into smaller components and reduce unnecessary rendering. I might use a form library such as React Hook Form that can minimize unnecessary updates. I would also check whether expensive validation, calculations, or API calls are happening on every keystroke.

How would you implement search with an API without sending a request for every keystroke?

I would implement debouncing. For example, if the user types customer, I would wait for a short period after the last keystroke before making the API call. I would also cancel or ignore outdated requests so that a slower response for an older search does not overwrite the newer search results.

Your React page contains a very expensive calculation that runs every time the component renders. How would you optimize it?

I would first profile the application to verify that the calculation is actually causing the performance problem. If it is expensive and its inputs do not change frequently, I could use useMemo to memoize the result. I would also consider moving the calculation to the backend if the operation is large or unnecessary for the browser.

Architecture & State

State Sharing & Cache

Global state management, context limits, Redux comparisons, and query caching logic.

You have a dashboard with multiple components that need the same user information. How would you share that data?

For application-wide state such as authenticated user information, I could use React Context or a state-management solution such as Redux Toolkit. If the data comes from an API, I would also consider a server-state library such as TanStack Query rather than putting all server data into Redux. The important point is to separate global client state from server/cache state.

Your React component is showing stale data after an API update. What would you check?

I would first determine whether the backend actually returned the updated data. Then I would check the React state update and whether I am mutating an existing state object instead of creating a new one. If the application uses a caching library, I would also check whether the relevant query/cache was invalidated or updated after the mutation.

When would you use Redux instead of React Context?

I would use Context for relatively simple global values such as theme, authentication information, or configuration. For a large application with complex client-side state, many independent state updates, middleware requirements, or extensive debugging requirements, Redux Toolkit can provide a more structured approach. I would not automatically use Redux for every application because Context can be sufficient for simpler requirements.

Security & Navigation

Routing, Auth & Security

Protected routes, session persistence, handling token expiration, and single-page routing challenges.

Your React application needs to maintain a user's login state after refreshing the browser. How would you implement it?

I would keep the authentication state in a central authentication mechanism and persist the appropriate session information so that a browser refresh does not completely lose the user's authenticated state. In a typical enterprise application, I would prefer secure, HTTP-only cookies for session or refresh-token handling rather than storing sensitive tokens in localStorage, because JavaScript-accessible storage increases the impact of XSS. On application startup, the frontend can call a backend endpoint to determine whether the session is still valid and then populate the authentication state.

Your API returns 401 Unauthorized after the user's access token expires. What should the React application do?

I would intercept the API response, determine whether the access token has expired, and attempt to obtain a new access token using the appropriate refresh mechanism. If the refresh succeeds, I would retry the original request. If the refresh fails, I would clear the authentication state and redirect the user to the login page. I would also prevent multiple simultaneous API requests from triggering multiple refresh operations.

How would you protect routes such as /admin and /dashboard in React?

I would create a protected route or authorization wrapper that checks the user's authentication and authorization state before rendering the protected component. Authentication should ultimately be enforced by the backend as well. React route protection is primarily a user-experience and navigation mechanism; it should never be considered the actual security boundary.

Your React application works on / but refreshing /dashboard returns 404. Why?

This commonly happens with client-side routing. React Router handles /dashboard inside the browser, but when the browser directly requests /dashboard, the web server may look for a physical /dashboard file or directory and return 404. I would configure the server to redirect unknown frontend routes to index.html so that React Router can handle the route.

Deployment & Forms

User Actions, Errors & Deployment

Disabling submit buttons, global error handling, and blank screen deployment troubleshooting.

A user clicks the Submit button multiple times and multiple orders are created. How would you solve this?

On the frontend, I would disable the button while the request is being processed and show a loading state. However, I would not rely only on React for this because a user can still send duplicate requests through other mechanisms. The backend should implement idempotency using an idempotency key or another unique business identifier so that repeated requests do not create duplicate orders.

Your React application has a blank white screen after deployment. How would you troubleshoot it?

I would first open the browser developer console and check for JavaScript errors. Then I would inspect the Network tab for failed JavaScript bundles, incorrect paths, API failures, CORS errors, or environment configuration problems. I would also verify the production build and routing configuration. If the application is deployed behind a web server, I would check whether SPA fallback routing is configured correctly.

How would you handle API errors globally in a React application?

I would centralize API communication instead of putting duplicated error-handling logic in every component. For example, with Axios I could configure interceptors to handle common responses such as 401, while individual components handle business-specific errors. I would also provide a consistent user-facing error mechanism such as toast notifications or an error boundary where appropriate.

Production Troubleshooting

Spring Boot & Cloud Scenarios

Real-world Spring Boot, Kafka, ECS, Kubernetes, and AWS production troubleshooting scenarios for senior engineer interviews.

Our Spring Boot API suddenly returns 503. How do you troubleshoot?

First, I would identify where the 503 is coming from—whether it is the application, load balancer, API Gateway, or another infrastructure component. I would check the ALB target health, ECS or Kubernetes task/pod status, application logs, and Spring Boot health endpoints such as /actuator/health. Then I would check CPU, memory, database connectivity, and downstream services. I would also look for any recent deployment or configuration changes. If the issue started immediately after a deployment, I would roll back first to restore the service and then investigate the root cause.

Your API latency increased from 200 ms to 5 seconds. What do you check?

I would first use application metrics and distributed tracing to determine where the additional four or five seconds are being spent. I would check database query performance, connection pool usage, external API calls, Kafka operations, CPU, memory, garbage collection, thread pool exhaustion, and network latency. I would also compare the current deployment with the previous version to see whether there was a recent code or configuration change. For example, if tracing shows that the application itself takes only 100 milliseconds but a database query takes 3.8 seconds, then I would focus on the database rather than simply increasing the number of application instances.

Kafka consumer lag is increasing. What could cause it?

Consumer lag generally means that producers are producing messages faster than consumers can process them. I would first check the producer rate, consumer processing rate, number of partitions, number of active consumers, and lag per partition. Then I would check whether the consumer is spending too much time processing messages, waiting on a database or external API, retrying failed messages, or experiencing frequent rebalancing or garbage collection pauses. If the application has enough partitions, I could increase the number of consumer instances to increase parallelism. I would also optimize the consumer processing logic or move expensive operations to asynchronous processing if necessary.

Database connection pool is exhausted. Why?

A connection pool becomes exhausted when all available database connections are being used and new requests have to wait for a connection. I would check whether there are slow queries, long-running transactions, connection leaks, or an increase in application traffic. I would also look at the HikariCP metrics to understand the number of active, idle, and waiting connections. I wouldn't simply increase the connection pool size because that could overload the database. I would first identify why connections are being held for too long and optimize the queries or transaction boundaries.

ECS task keeps restarting. How do you debug it?

I would first look at the ECS service events and the stopped-task reason to understand why the task is being terminated. Then I would check the container exit code, CloudWatch logs, CPU and memory usage, health-check configuration, load balancer target health, environment variables, secrets, IAM permissions, and the container image. Common causes are application startup failures, out-of-memory errors, failed health checks, incorrect ports, missing configuration, or permission issues. If the application starts successfully but ECS keeps replacing it, I would pay particular attention to the health-check configuration and whether the application is actually ready to receive traffic.

Kubernetes pod is running but service cannot reach it. What do you check?

I would trace the request path from the Kubernetes Service to the pod. First, I would verify that the pod is actually ready and that its readiness probe is passing. Then I would check the Service selector and make sure it matches the labels on the pod. I would also verify the Service targetPort matches the container port and check the Service endpoints or EndpointSlices to make sure the Service actually has healthy pods behind it. After that, I would investigate NetworkPolicies, DNS, Ingress configuration, and namespace issues. A common problem is that the pod is running but the Service selector doesn't match the pod labels, so the Service has no endpoints.

How do you deploy a zero-downtime Spring Boot application?

I would deploy multiple instances of the Spring Boot application behind a load balancer and use a rolling deployment strategy. New instances would start while the old instances are still serving traffic, and the load balancer would only send traffic to instances that pass their health and readiness checks. Once the new instances are healthy, traffic would gradually move to them and the old instances would be terminated gracefully. I would also make sure database changes are backward compatible because during a deployment, old and new versions of the application may temporarily run at the same time. In Kubernetes, I would use readiness probes and a RollingUpdate strategy with appropriate maxUnavailable and maxSurge settings.

How would you scale a service from 100 requests/sec to 10,000 requests/sec?

I wouldn't immediately start adding servers. First, I would identify the bottleneck by looking at application latency, CPU, memory, database performance, connection pools, external service latency, and Kafka throughput. I would make the application stateless and use horizontal scaling through ECS or Kubernetes autoscaling. For frequently accessed data, I would introduce Redis caching, and for expensive operations that don't need to happen synchronously, I would use Kafka or SQS to process them asynchronously. I would also optimize database queries, add appropriate indexes, and consider read replicas if database reads become the bottleneck. Finally, I would perform load testing and monitor P95 and P99 latency, error rate, throughput, CPU, database connections, and Kafka lag.

How would you prevent duplicate Kafka message processing?

Kafka consumers can process the same message more than once, so I would design the consumer to be idempotent. For example, each message could contain a unique event ID, and before processing the event I could check whether that event has already been processed. I could store the event ID in a database table with a unique constraint and skip the processing if it already exists. This way, even if Kafka redelivers the message after a consumer failure, the business operation won't happen twice. I would generally prefer idempotency rather than relying on exactly-once behavior across Kafka and an external database.

How would you implement retry without creating duplicate orders?

I would use an idempotency key for the order creation request. For example, the client could send an Idempotency-Key with the request, and I would store that key with the created order in the database with a unique constraint. If the client retries because of a timeout, the application can recognize that the same request was already processed and return the existing order instead of creating another one. For temporary failures, I could use Resilience4j with limited retries and exponential backoff, but I would only retry transient errors. I would not retry validation or business errors because retrying those would not solve the problem.

How would you secure communication between microservices?

I would secure service-to-service communication using authentication, authorization, and encryption. For authentication, I could use OAuth2 or JWT-based service credentials, while TLS would encrypt the communication between services. For highly sensitive environments, I could also use mutual TLS so that both services verify each other's identity. I would apply authorization to make sure a service can only access the APIs and resources it actually needs. At the infrastructure level, I would keep services in private networks where possible and use security groups and network policies to restrict unnecessary communication.

How would you store passwords/secrets in AWS?

I would use AWS Secrets Manager for sensitive information such as database passwords, API keys, and OAuth credentials. The Spring Boot application would access the secret using an IAM role rather than storing credentials directly in the source code or configuration file. I would follow least-privilege access so that the application can only retrieve the secrets it actually needs. For less-sensitive configuration, AWS Systems Manager Parameter Store could also be used. I would never commit passwords or API keys to Git or hardcode them in the Docker image.

How would you design an application for multi-AZ failure?

I would make the application and its major dependencies available across multiple Availability Zones. For example, I could deploy ECS tasks or Kubernetes pods across at least two or three AZs behind an Application Load Balancer. If one AZ becomes unavailable, the load balancer can route traffic to healthy instances in another AZ. The database should also use a Multi-AZ configuration, and services such as Kafka should have replicas distributed across AZs. I would also use autoscaling and health checks so that unhealthy instances are automatically replaced. Finally, I would actually test failure scenarios rather than assuming the architecture is resilient.

How would you migrate a monolith into microservices?

I would avoid rewriting the entire monolith at once because that creates significant risk. Instead, I would use the Strangler Fig approach, where I gradually extract individual business capabilities from the monolith into independent services. I would first identify clear business boundaries, such as customer, order, payment, or notification, and start with a relatively isolated and low-risk component. I would expose the new service through an API or event-based communication and gradually move traffic from the monolith to the new service. Over time, I would continue extracting additional services while maintaining backward compatibility and observability. I would also be careful about shared databases because simply creating multiple services while keeping tightly coupled database access doesn't provide the full benefits of microservices.

How would you design a system where one service is unavailable for 30 minutes?

I would design the system so that the unavailable service doesn't bring down the entire application. If the operation doesn't fundamentally require that service to complete, I would use asynchronous messaging with Kafka or SQS. For example, when an order is created, the Order Service can save the order and publish a notification event to Kafka. If the Notification Service is unavailable for 30 minutes, the event remains in Kafka and can be processed when the service comes back online. I would also use timeouts, circuit breakers, retries with exponential backoff, dead-letter queues, and idempotent consumers. The key principle is to avoid creating a synchronous dependency on a service when the business operation can continue without it.
