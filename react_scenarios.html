Core Guide
State & Lifecycle

React Hooks & Lifecycle

Common hooks like useEffect, useState, useRef, rendering behaviors, and Strict Mode side effects.

Your React page is making the same API call multiple times when the component loads. What could be wrong?

Usually I would first check the useEffect dependency array. If useEffect does not have the correct dependency array, it can execute more often than expected. I would also check whether React Strict Mode is enabled in development, because React can intentionally run certain lifecycle logic twice in development to identify side effects. I would make sure the API call is inside useEffect with the appropriate dependencies and that the effect has proper cleanup when necessary.

A parent component changes state and a child component re-renders unnecessarily. How would you troubleshoot it?

I would use React DevTools Profiler to determine why the child is rendering. If the child receives objects, arrays, or functions created during every parent render, their references change even if their values are the same. I could use React.memo for the child and useMemo or useCallback for expensive values or callbacks when appropriate. I would avoid blindly using memoization everywhere because it also introduces complexity.

How would you handle loading, success, and error states for an API call?

I would explicitly model the request state instead of relying on a single boolean. For example, the UI should be able to distinguish between initial loading, successful data retrieval, empty results, and an error. With a server-state library, much of this state management is already provided. For a simple application, I could manage it using React state and useEffect.

What is the difference between useMemo and useCallback?

useMemo memoizes the result of a calculation, while useCallback memoizes the function reference itself. For example, I might use useMemo when calculating an expensive filtered dataset and useCallback when passing a callback to a memoized child component. I would use them based on an actual performance problem rather than automatically adding them everywhere.

Your React component receives new props but does not display the updated value. What could be wrong?

I would check whether the component is incorrectly memoized, whether the parent is mutating an object instead of creating a new reference, and whether the component has copied props into local state and that state has become stale. React relies heavily on state and prop references, so directly mutating objects or arrays can prevent expected updates.

A user navigates away from a page while an API request is still running. What would you do?

I would clean up the request when the component unmounts. With the Fetch API, I could use AbortController to cancel the request. This prevents unnecessary work and helps avoid updating state after the component is no longer relevant.

Performance & Virtualization

React Performance & Scaling

Optimizing render throughput, virtual lists, form performance, search debouncing, and expensive browser-side calculations.

Your React application becomes very slow when displaying 10,000 records. How would you improve it?

I would first determine whether the problem is rendering, API response time, or data processing. On the React side, I would avoid rendering all 10,000 records at once and use pagination or list virtualization. I could use techniques such as React.memo, useMemo, and useCallback where they actually reduce unnecessary work. I would also make sure the backend supports pagination rather than returning the entire dataset to the browser.

Your React application has a large form with 50 fields and typing becomes slow. What would you investigate?

I would profile the component first. If every keystroke causes the entire form to re-render, I would break the form into smaller components and reduce unnecessary rendering. I might use a form library such as React Hook Form that can minimize unnecessary updates. I would also check whether expensive validation, calculations, or API calls are happening on every keystroke.

How would you implement search with an API without sending a request for every keystroke?

I would implement debouncing. For example, if the user types customer, I would wait for a short period after the last keystroke before making the API call. I would also cancel or ignore outdated requests so that a slower response for an older search does not overwrite the newer search results.

Your React page contains a very expensive calculation that runs every time the component renders. How would you optimize it?

I would first profile the application to verify that the calculation is actually causing the performance problem. If it is expensive and its inputs do not change frequently, I could use useMemo to memoize the result. I would also consider moving the calculation to the backend if the operation is large or unnecessary for the browser.

Architecture & State

State Sharing & Cache

Global state management, context limits, Redux comparisons, and query caching logic.

You have a dashboard with multiple components that need the same user information. How would you share that data?

For application-wide state such as authenticated user information, I could use React Context or a state-management solution such as Redux Toolkit. If the data comes from an API, I would also consider a server-state library such as TanStack Query rather than putting all server data into Redux. The important point is to separate global client state from server/cache state.

Your React component is showing stale data after an API update. What would you check?

I would first determine whether the backend actually returned the updated data. Then I would check the React state update and whether I am mutating an existing state object instead of creating a new one. If the application uses a caching library, I would also check whether the relevant query/cache was invalidated or updated after the mutation.

When would you use Redux instead of React Context?

I would use Context for relatively simple global values such as theme, authentication information, or configuration. For a large application with complex client-side state, many independent state updates, middleware requirements, or extensive debugging requirements, Redux Toolkit can provide a more structured approach. I would not automatically use Redux for every application because Context can be sufficient for simpler requirements.

Security & Navigation

Routing, Auth & Security

Protected routes, session persistence, handling token expiration, and single-page routing challenges.

Your React application needs to maintain a user's login state after refreshing the browser. How would you implement it?

I would keep the authentication state in a central authentication mechanism and persist the appropriate session information so that a browser refresh does not completely lose the user's authenticated state. In a typical enterprise application, I would prefer secure, HTTP-only cookies for session or refresh-token handling rather than storing sensitive tokens in localStorage, because JavaScript-accessible storage increases the impact of XSS. On application startup, the frontend can call a backend endpoint to determine whether the session is still valid and then populate the authentication state.

Your API returns 401 Unauthorized after the user's access token expires. What should the React application do?

I would intercept the API response, determine whether the access token has expired, and attempt to obtain a new access token using the appropriate refresh mechanism. If the refresh succeeds, I would retry the original request. If the refresh fails, I would clear the authentication state and redirect the user to the login page. I would also prevent multiple simultaneous API requests from triggering multiple refresh operations.

How would you protect routes such as /admin and /dashboard in React?

I would create a protected route or authorization wrapper that checks the user's authentication and authorization state before rendering the protected component. Authentication should ultimately be enforced by the backend as well. React route protection is primarily a user-experience and navigation mechanism; it should never be considered the actual security boundary.

Your React application works on / but refreshing /dashboard returns 404. Why?

This commonly happens with client-side routing. React Router handles /dashboard inside the browser, but when the browser directly requests /dashboard, the web server may look for a physical /dashboard file or directory and return 404. I would configure the server to redirect unknown frontend routes to index.html so that React Router can handle the route.

Deployment & Forms

User Actions, Errors & Deployment

Disabling submit buttons, global error handling, and blank screen deployment troubleshooting.

A user clicks the Submit button multiple times and multiple orders are created. How would you solve this?

On the frontend, I would disable the button while the request is being processed and show a loading state. However, I would not rely only on React for this because a user can still send duplicate requests through other mechanisms. The backend should implement idempotency using an idempotency key or another unique business identifier so that repeated requests do not create duplicate orders.

Your React application has a blank white screen after deployment. How would you troubleshoot it?

I would first open the browser developer console and check for JavaScript errors. Then I would inspect the Network tab for failed JavaScript bundles, incorrect paths, API failures, CORS errors, or environment configuration problems. I would also verify the production build and routing configuration. If the application is deployed behind a web server, I would check whether SPA fallback routing is configured correctly.

How would you handle API errors globally in a React application?

I would centralize API communication instead of putting duplicated error-handling logic in every component. For example, with Axios I could configure interceptors to handle common responses such as 401, while individual components handle business-specific errors. I would also provide a consistent user-facing error mechanism such as toast notifications or an error boundary where appropriate.
